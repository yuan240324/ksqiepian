# 06 - 故障背景

这份文档说明**为什么会走到「拉官方回放」这条路**。如果只是想把回放抓下来，
看 [`01-快速开始.md`](01-快速开始.md) 就够了。

---

## 6.1 事故现象

一次直播录制（快手主播「王者荣耀轩妹妹（圆梦主播）」，ID `YyXx-828924`）结束后，
录制目录里的文件状态如下：

| 文件 | 目录里显示的尺寸 | 能否读取 |
| --- | --- | --- |
| `recorder.log` | 21913 B | 能，但只能读出前 1776 B |
| `relink.log` | 366 B | 能 |
| `ffmpeg_err.log` | 3459 B | 能 |
| `启动录制.cmd` | 414 B | **不能**（err=2） |
| `YyXx-828924_20260916_202834_001_000.ts` | **1,770,201,232 B** | **不能**（err=2） |

**核心症状：文件在目录列表里能看到完整尺寸，但打不开。**

```text
CreateFileW 返回 ERROR_FILE_NOT_FOUND (2)
```

尺寸、类型、路径长短都不相关——1.65 GB 的 `.ts` 和 414 字节的 `.cmd` 同样打不开。

---

## 6.2 排查过程

### ① 硬盘坏了吗？—— 没有

```
chkdsk G: /scan
  310272 个文件记录已处理
  0 个错误
  0 个坏扇区
  Windows 已扫描文件系统并且没有发现问题
```

```
WDC WD20EZRX-00D8PB0   Healthy
CT240BX200SSD1         Healthy
```

**物理盘健康，文件系统无错误。** 排除了坏道和数据覆盖。

### ② 是中文路径 / 权限问题吗？—— 不是

- 同目录下英文名文件能读，中文名 `启动录制.cmd` 不能读 → 但另有中文名的日志能读 → **不是中文问题**
- ACL 里确实缺少 `G50\weido` 条目，但补齐后仍不可读 → **不是权限问题**
- 用 `\\?\` 长路径前缀、`FileShare.ReadWrite`、管理员权限，全部 err=2 → **不是共享模式问题**

### ③ 用 MFT 文件记录 ID 定位 —— 找到了分界线

直接读 NTFS MFT，按文件记录号对比：

| 文件 | MFT 记录号 | 结果 |
| --- | --- | --- |
| `recorder.log` | `...0x0004...0x00011176` | 可读 |
| `relink.log` | `...0x0003...0x0001117f` | 可读 |
| `ffmpeg_err.log` | `...0x0003...0x0001117d` | 可读 |
| `启动录制.cmd` | — | err=2 |
| `YyXx-...001_000.ts` | — | err=2 |

规律清楚了：**能读和不能读的分界线，正好落在 MFT 记录是否失效上**。
目录项（`$I30` 索引）还挂着这些文件的名字和尺寸，
但对应的 **MFT 记录已经损坏**，于是：

- 目录枚举：读 `$I30` 索引 → **显示得出来**
- 打开文件：要读 MFT 记录拿数据运行列表（data runs）→ **记录坏了，返回 err=2**

这就是「看得见、摸不着」的经典 **悬空目录项（dangling directory entry）**。

### ④ 卷影副本能救吗？—— 没有

```powershell
vssadmin list shadows /for=G:
# 找不到满足条件的文件
```

**没有卷影副本可回滚。**

## 6.3 数据恢复尝试

从官方回放拉片之前，先把「直接从坏盘里抠数据」这条路走完。

### 方案 A / B：读 MFT 数据运行列表

思路：既然目录项还在，就顺着它找 MFT 记录，从记录里解析 `$DATA` 属性的数据运行列表（data runs），
拿到 LCN 序列后按物理偏移直接读扇区。

**失败。** MFT 记录本身已损坏，数据运行列表读不出来。

### 方案 C：只读扇区扫描 + `$Bitmap` 交叉验证（已执行）

不依赖任何元数据，从**物理卷**层面操作：

```text
1. 用 P/Invoke 打开 \\.\PhysicalDrive1        （CreateFileW + SetFilePointerEx + ReadFile）
2. 解析 NTFS $Bitmap，得到全部「已占用簇」
3. 用 TS 特征（每 188 字节一个 0x47 sync byte）全盘扫
4. 与 $Bitmap 交叉验证，排除已被其他文件覆盖的区域
```

> 全程**只读**，不写盘，避免覆盖尚未恢复的数据。

#### `$Bitmap` 解析结果

```text
bitmap bytes read : 9,600,000
used clusters     : 20,808,745
换算容量          : 20,808,745 * 4096 = 79.38 GB
碎片区间数        : 477
与 chkdsk 对照    : 82,450,168 KB ≈ 78.6 GB   ✔ 一致
```

交叉验证通过，说明 `$Bitmap` 解析正确。

#### 候选块定位

```text
LCN 区间    : 31573815 ~ 31988505
大小        : 414,691 簇 = 1619.9 MB   （与 1688 MB 目标接近）
物理偏移    : 1,685,875,570,688 B
```

尺寸高度吻合，看起来有戏。

#### 验证候选块 —— 失败

把候选块的前 16 字节读出来：

```text
2F 2A 2A 0A 20 2A 20 54 65 73 74 73
/*\n * Tests
```

**这是一个 JavaScript 测试文件**（`/**\n * Tests for ...`），不是视频。

进一步用 TS 特征率复核：

```text
188 字节对齐的 0x47 sync byte 占比 = 0.09%
```

随机数据里出现 `0x47` 的概率约 1/256 = 0.39%，实测 0.09% **比随机还低**。
判定：**该区域与目标视频无关**。

#### 回收站 —— 也是空的

用户提示回收站里看到了 `.ts` 文件，实际检查：

```text
$Recycle.Bin 下的 .ts 文件全部为 0 MB 空壳
```

**只有目录项，没有数据。**

## 6.4 结论：本地恢复不可行

| 路径 | 结果 |
| --- | --- |
| 正常打开文件 | err=2，MFT 记录损坏 |
| 读 MFT 数据运行列表 | 记录损坏，无法解析 |
| `$Bitmap` + 扇区扫描 | 候选块是 JS 文件，非视频 |
| 回收站 | 只有 0 字节空壳 |
| 卷影副本 | 不存在 |
| 物理盘 / 文件系统 | 健康（chkdsk 0 错误） |

**原始 1.65 GB 录制文件已不可恢复。**
数据大概率在录制期间就被重写（录制程序反复重启、`relink` 重连导致文件被反复创建/截断），
而文件系统元数据没能同步更新。

## 6.5 转向：拉官方直播回放

既然本地救不回来，唯一的路是**从源头重新拿一份**。

当时的疑虑是「快手只给短链，很难解码」。实测发现这个判断是错的：

```text
分享口令   ##X56ZfKJb622Z1i7##
   ↓ 拼成短链
短链       https://v.kuaishou.com/f/X56ZfKJb622Z1i7
   ↓ 跟随 302（移动端 UA）
回放页     https://v.kuaishou.com/fw/playback/1499544558?subBiz=LIVE_PLAYBACK
   ↓ 正则捞 m3u8
直链       .../JsQSVN0Ra3Q_GameAvcHdL1Lto.1789558283798-5163925.0-16.m3u8
   ↓ 8 线程下载 1293 片
merged.ts  944.4 MB
   ↓ PyAV 透传重封装（8 秒）
成品        901.2 MB MP4，86 分 06 秒，1280x960@30fps，带声音
```

**短链不是一个需要逆向的加密串，它只是一个不透明 token——跟随重定向就能拿到真实地址。**

## 6.6 两条经验

### ① 录播要「边录边落盘 + 双写」

本次事故的根因是文件元数据与数据不同步。如果录制期间：
- 分片滚动落盘（每个分片 2~4 秒，损坏只丢一个分片）
- 关键分片做一份副本到另一块盘

就不会出现「整场 1.65 GB 全部不可读」的最坏情况。

### ② 云侧才是最终兜底

只要直播开了回放（`subBiz=LIVE_PLAYBACK`），平台就替你存了一份完整录像。
**本地录制失败时，第一反应应该是去确认云端有没有回放，而不是先做深度数据恢复。**
本项目就是走了「深度恢复 → 全部失败 → 转向云端」的弯路，
虽然最终成功，但多花了几小时。顺序反过来会高效得多。

## 6.7 相关脚本

坏盘排查用到的 PowerShell 脚本（纯只读）：

| 脚本 | 作用 |
| --- | --- |
| `diag.ps1` | 卷信息 / 物理盘健康 / ACL 检测 |
| `bitmap.ps1` | 解析 `$Bitmap`，统计已占用簇与碎片区间 |
| `verify.ps1` | 读候选 LCN 区域，做 TS sync byte 特征率判定 |

这些脚本属于**排障工具**，不在提取链路内，故未收录到 `ks_extract/`。
